# Store packaging: runtime choices, manifest variants and the Certification Kit (2026-10-30)

Task 0 of the phase 5 slice 4 plan. Measured on the Windows 11 ARM64 VM (build 26200, Parallels) and on the GitHub-hosted runners `windows-latest` (x64) and `windows-11-arm` (ARM64), in a throwaway copy of the repository with its identity renamed `BinaryCompanion.TimeTug.Spike` (so the VM's development install was never touched). Every package was built with `dotnet publish -c Release -p:GenerateAppxPackageOnBuild=true`, signed with a throwaway certificate, installed for the current user, started through `shell:AppsFolder` (the release manifests have no execution alias), and checked 12 seconds later for a running `TimeTug` process and a log file with its first entries. Sizes are the `.msix` file; "framework packages" are the four `Dependencies\<arch>\*.msix` (Windows App Runtime 2.x and its VC libraries) that a framework-dependent package needs on the machine.

## Answers

**(a) Can a self-contained package be built and installed on both architectures, and what does it cost?** Yes. `WindowsAppSDKSelfContained=true` builds, installs and runs on x64 and ARM64 (runner and VM). Bundling the Windows App SDK runtime costs about 29 MB over v5 (120.2 against 91.2 MB on x64) and removes the need for the four framework packages (135 MB on disk, installed once per machine). It must not be passed on the command line: the class libraries that reference the Windows App SDK refuse it ("WindowsAppSDKSelfContained should not be applied to a class library"), so the app project sets it from its own `Flavour` property. Setting `SelfContained=true` (the .NET runtime) also gives the build a runtime identifier, which stops the package carrying the other architecture's native libraries: v2's x64 package contained `runtimes\win-arm64\native\*` (the engine's Swift runtime) and was 24 MB larger than v5 for it.

**(b) Does the Store accept a framework-dependent package, and which is the default for the Store flavour?** The .NET runtime must be bundled in every release flavour: v2 and v3 start on a developer machine only because the SDK put the .NET 10 desktop runtime there, and a Store customer has none. For the Windows App SDK runtime the Store's documented behaviour is that it installs a framework package dependency automatically (the Windows App Runtime packages are published in the Store), and Microsoft recommends the framework-dependent form for Store apps; that is what v5 is. It cannot be tried without a submission, so it stays an assumption until the first flight (phase 9). **Decision:** Store = v5 (.NET bundled, Windows App SDK as a framework dependency): the smallest package (91 MB), the fewest Certification Kit findings, and the form Microsoft recommends. Direct = v4 (both bundled): a sideloaded package has no Store to resolve the dependency, and v4 installs on a clean PC with nothing else. If the first flight shows the Store cannot resolve the dependency, `-p:ReleaseWindowsAppSdkSelfContained=true` makes the Store package v4 with no other change (that switch was built and run here). Cost of the decision: the Store package depends on the Windows App Runtime framework package (updated by the Store); the Direct package carries its own copy (updated only when the app is) and is 29 MB larger.

**(c) Can the manifest drop the `uap5:ExecutionAlias` by a conditional?** Yes, with a manifest per flavour rather than a transform. The packaging targets include `Package.appxmanifest` automatically only while no `AppxManifest` item exists; naming an `AppxManifest` item in the project (conditional on the `Flavour` property) selects `Package.Store.appxmanifest` or `Package.Direct.appxmanifest` instead, and a build can hand any other file in with `-p:ReleaseManifestPath`. A manifest with Partner Center placeholders cannot be packaged (`MakeAppx` rejects `__PARTNER_CENTER_PACKAGE_NAME__` against the schema pattern `[-.A-Za-z0-9]+`), which is useful: a build that forgot to fill an identity value fails instead of shipping a placeholder. An architecture test keeps the three manifests identical except for identity, the alias and the COM class ids. Each flavour has its own toast activator class id: two packages registering the same COM class would collide when both are installed.

**(d) What does the Windows App Certification Kit say?** It runs on the x64 runner and nowhere else here. The ARM64 runner's kit folder holds only `SupportedAPIs-x64.xml` (no `appcert.exe`), and the VM has no Windows SDK kit at all (installing one would be a download from Microsoft that this work did not make). On x64 every variant, the development package included, ends with an overall PASS. The only failures are optional tests: **Blocked executables** in every variant (the Swift runtime DLLs, `coreclr.dll`, the Windows App SDK bootstrap and `System.Diagnostics.Process.dll` import `CreateProcessW` or `ShellExecuteExW`; the Store policy treats this test as a warning, and the engine's runtime is not ours to change) and, only when the Windows App SDK is bundled (v3, v4), **General metadata correctness** (`Microsoft.UI.Xaml.winmd` re-declares GUIDs that `Windows.UI.Xaml` already has, a known false report for the bundled WinUI metadata). That is one more reason the Store flavour keeps the framework dependency. So the Certification Kit is a gate on x64 only: the release dry run runs it there and uploads the report; the ARM64 package is checked by `check-release-package.ps1` and by installing it.

## What it changed in the plan

- Task 2 builds the release flavours with `SelfContained=true` always, and `WindowsAppSDKSelfContained=true` for Direct (and for Store only with `ReleaseWindowsAppSdkSelfContained=true`), both set inside `TimeTug.App.csproj` from the `Flavour` property.
- Manifests are separate files (`Package.Store.appxmanifest`, `Package.Direct.appxmanifest`), not a transform; the build script fills the identity values and the version into a copy.
- WACK in the dry run is x64 only and its report is uploaded; the overall result must be PASS (optional findings are listed, not failures). The plan's "non-blocking on ARM64 if it cannot run there" applies: it cannot.

## Not observed

- Installing a release-shaped package from the Store (needs a submission; phase 9's first flight).
- A clean PC without the Windows App Runtime installing v5 from a Store listing: the dependency resolution is the Store's documented behaviour, not seen here. Sideloading v5 on a PC lacking the framework packages fails (the development install scripts pass the four packages along).
- Toast button activation from a release package (needs a person at the screen; manual checklist).
